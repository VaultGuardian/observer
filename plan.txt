TIER 1 — REAL BUGS / VERDICT-PATH ISSUES
========================================================================

[1.1] Advertised feature does not exist: hostname + server IP in alert emails
  CLAIM (README:226-227, README:264, README:316-318; also install.sh:244-249
  comment and the installer prompt "Server nickname (used in alert emails)"):
  "escalation emails include the HOSTNAME (above) and the server's primary IP,
  so it's obvious which machine fired the alert."
  ACTUAL: HOSTNAME is loaded into cfg.SelfID (config.go:118) and used ONLY to
  skip Observer's own container logs (main.go:415 → w.SetSelfID;
  internal/watcher/watcher.go:67-68). The notifier.Alert struct
  (internal/notifier/notifier.go:37-49) has no hostname or IP field; the email
  formatter (internal/notifier/email.go) never inserts either; nothing in the
  codebase computes a "primary IP" at all. The installer collects the nickname
  (install.sh:248-249) and writes HOSTNAME=$SERVER_NICK (install.sh:426), but
  the value never reaches an email.
  PROOF: config.go:118; main.go:415; internal/watcher/watcher.go:67-68;
  internal/notifier/notifier.go:37-49; grep of internal/notifier/ shows no
  hostname/IP usage.
  RECOMMENDED FIX (FEATURE TO BUILD — not a doc deletion):
    - Add Hostname and ServerIP fields to notifier.Alert
      (internal/notifier/notifier.go:37).
    - Thread cfg.SelfID into the dispatcher or into every Alert construction
      site (resultrouter.go:357, resultrouter.go:426, main.go:1325); simplest
      is a Dispatcher-level field set once at startup in main.go so individual
      call sites don't change.
    - Compute primary IP once at startup (e.g. UDP-dial trick or first
      non-loopback interface addr) and set it alongside.
    - Render both in the email subject/body in
      internal/notifier/email.go (formatEmailHTML) and in webhook payloads
      (internal/notifier/webhook.go) for parity.
    - Fallback when HOSTNAME env is empty: os.Hostname() (also fixes [2.2]).

[1.2] "policy" verdict documented but never produced by the verdict path
  CLAIM (README:166, verdict table): verdict `policy` — "Operator-defined deny
  rules. Always escalates regardless of outcome. Emails: Yes"
  ACTUAL: There is no `policy` verdict anywhere in the verdict path. Policy
  outcomes are routed in routePolicyOutcome (main.go:1296-1355):
    - action "escalate" → stored Finding has Verdict "malicious",
      Classification "policy_escalated" (main.go:1346-1347), email dispatched
      (main.go:1338).
    - action "alert" → Verdict "alert", Classification "policy_alert"
      (main.go:1312-1313), NO email (Notified: false, main.go:1318).
    - action "allow" → log line only, no finding (main.go:1298-1300).
  Querying the API for verdict=policy returns nothing, ever.
  PROOF: main.go:1296-1355; internal/store/types.go:38 (verdict list has no
  "policy"); internal/policy/types.go.
  RECOMMENDED FIX: Either (a) introduce a real `policy` verdict in the store
  and routePolicyOutcome so the documented contract holds, or (b) rewrite the
  table row to say policy escalations surface as `malicious` with
  classification `policy_escalated`. (a) matches the README contract; (b) is
  the smaller change. Decide before touching docs.

[1.3] RESULT OF THE "POLICY ALWAYS ESCALATES" CHECK: FALSE
  CLAIM (README:166): policy "Always escalates regardless of outcome."
  ACTUAL: The policy engine has three actions — allow / alert / escalate
  (internal/policy/engine.go:175-309):
    - ssh_login → escalate, but ONLY for non-trusted IPs; trusted IPs hit the
      allowlist check (engine.go:125, e.store.IsTrustedIP) and resolve to
      allow.
    - useradd (engine.go:208-221) → escalate
    - privilege_grant / usermod -aG sudo (engine.go:227-246) → escalate
    - authorized_keys (engine.go:250-261) → escalate
    - sudo_failure (engine.go:276-288) → alert (NOT escalate, NO email;
      main.go:1302-1319 stores a finding with Notified=false)
  So two of the documented policy paths (trusted-IP SSH login, failed sudo)
  do not escalate and do not email.
  PROOF: internal/policy/engine.go:125, 175-309; main.go:1296-1355.
  RECOMMENDED FIX: Correct the verdict-table row and the "What it catches"
  bullet ("Failed sudo attempts → alert" at README:329 is actually consistent;
  the verdict table at README:166 is the contradicting line).

[1.4] Pipeline diagram order does not match the code
  CLAIM (README:86-120 diagram; README:124-133 layer list): order is
  deterministic filters → policy engine → seed patterns → pattern store → LLM,
  with "seed patterns" as a distinct stage before the pattern store.
  ACTUAL:
    - The policy engine runs FIRST, before the analyzer:
      makeLogHandler evaluates policyEngine.Evaluate(evt) at main.go:1410 and
      returns on match; a.Analyze() runs after, at main.go:1415.
    - The deterministic noise/probe filters live INSIDE Analyzer.Analyze
      (internal/analyzer/analyzer.go:164-253), i.e. after policy.
    - Seed patterns are NOT a separate stage: seedMaliciousPatterns loads them
      into the pattern store as contains-tier malicious entries
      (seeds.go:57-62 → patternstore SeedMaliciousPattern,
      internal/patternstore/store.go:665-690). They are matched during the
      ordinary pattern-store Match (analyzer.go:253), in tier order
      hash → prefix → regex → contains (store.go:363-394).
  True order: policy engine → deterministic filters → pattern store
  (seeds included, contains tier) → LLM.
  PROOF: main.go:1410-1415; internal/analyzer/analyzer.go:164-253;
  seeds.go:57-62; internal/patternstore/store.go:363-394, 665-690.
  RECOMMENDED FIX: Redraw the diagram and renumber the "Pipeline layers" list
  to the actual order; describe seeds as "curated contains-tier entries
  pre-loaded into the pattern store" rather than a separate stage. Note the
  ordering nuance that a hash-tier allow/suppress hit is checked before the
  contains-tier seeds within the store.

TIER 2 — USER-VISIBLE DOC-VS-CODE MISMATCHES
========================================================================

[2.1] Coordinator evidence hold is 5s/10s, not "2–5 s"
  CLAIM (README:54 "held 2–5 seconds"; README:130 "holds for evidence (2–5 s)").
  ACTUAL: DefaultEvidenceWindow = 5s, DefaultFinalizeWindow = 10s; the code
  comment says explicitly "v0.43.2+: Bumped from 2s/5s to 5s/10s to account
  for the full REC pipeline delay."
  PROOF: internal/coordinator/coordinator.go:51-56.
  RECOMMENDED FIX: Update both README references to "5 s evidence window
  (10 s finalize)".

[2.2] HOSTNAME config-table default is wrong
  CLAIM (README:264): HOSTNAME default "(system hostname)".
  ACTUAL: The binary's default is the empty string — getEnv("HOSTNAME", "")
  (config.go:118); there is no os.Hostname() fallback in the binary. Only the
  INSTALLER defaults the prompt to $(hostname) (install.sh:248) and writes it
  to the env file (install.sh:426). A manual install without HOSTNAME set gets
  "".
  PROOF: config.go:118; install.sh:248-249, 426.
  RECOMMENDED FIX: Either add an os.Hostname() fallback in config.go (pairs
  naturally with feature [1.1]) or change the table default to "(empty;
  installer defaults it to the system hostname)".

[2.3] Failed-probe status list inconsistent within the README; one spot wrong
  CLAIM (README:163, recon row): "hit a 404/403/410/405" — omits 400.
         (README:345): "400/403/404/405/410" — correct.
  ACTUAL: failedStatusCodes = {400, 403, 404, 405, 410}
  PROOF: internal/analyzer/analyzer.go:1035-1041.
  RECOMMENDED FIX: Add 400 to the recon-row list at README:163.

[2.4] CLI reference omits `vaultguardian rec status`
  CLAIM (README:236-245): CLI table lists status/logs/stats/update/update vX/
  restart/version/uninstall only.
  ACTUAL: An eighth subcommand `vaultguardian rec status` (REC coverage
  inspection) exists — added in commit 8775955 "api/cli: surface REC coverage
  status".
  PROOF: install.sh:559-614.
  RECOMMENDED FIX: Add the row `vaultguardian rec status  # REC coverage and
  port status` to the CLI block.

[2.5] Seed-pattern list in "What it catches" is incomplete
  CLAIM (README:331-335): four seed categories (credential file, RSA/OPENSSH
  private keys, bash reverse shell, curl|sh / wget|sh / base64|bash).
  ACTUAL: 11 seeds. Not mentioned: `nc -e /bin/sh` (netcat reverse shell),
  `rm -rf /` (destructive command), `BEGIN EC PRIVATE KEY`,
  `BEGIN PRIVATE KEY` (generic PKCS#8).
  PROOF: seeds.go:29-55.
  RECOMMENDED FIX: Either list all 11 or mark the list as representative
  ("including:").

TIER 3 — COSMETIC / FRAMING
========================================================================

[3.1] Project-structure tree omits files and misplaces the retry queue
  CLAIM (README:403-423): tree shows main.go/seeds.go/resultrouter.go/
  config.go/install.sh/internal/...; main.go annotated as "Pipeline wiring,
  coordinator, retry queue, reconciler".
  ACTUAL: Repo root also contains httpparse.go (+test), llmscheduler.go,
  reclasscache.go, config_test.go, resultrouter_test.go, release.sh, docs/,
  go.mod/go.sum, LICENSE. The bounded LLM retry/scheduler queue lives in
  llmscheduler.go, not main.go (main.go only wires it).
  PROOF: repo root listing; llmscheduler.go.
  RECOMMENDED FIX: Add the missing root files to the tree (at least
  httpparse.go, llmscheduler.go, reclasscache.go, release.sh, docs/) and move
  "retry queue" to llmscheduler.go's annotation.

[3.2] Notifier described as "Email (Resend), webhook" — understated
  CLAIM (README:417).
  ACTUAL: internal/notifier/ also contains apns.go (Apple Push), fcm.go
  (Firebase), sms.go.
  PROOF: internal/notifier/{email,webhook,apns,fcm,sms}.go.
  RECOMMENDED FIX: Update annotation, e.g. "Email (Resend), webhook, push
  (APNS/FCM), SMS" — or document why the extra channels are not yet
  user-facing if they're unreleased.

[3.3] `evidence_unavailable` is a resolution status, not a verdict
  CLAIM (README:119, 169): listed in the verdict diagram/table alongside
  recon/alert/malicious.
  ACTUAL: It is a resolution/coverage status stamped on findings by the
  reconciler (main.go:1444-1481, 15-min timeout, 60s sweep); the finding keeps
  its original verdict. Defined at internal/store/types.go:79, separate from
  the verdict list at types.go:38. Pattern-store buckets also have an internal
  "unknown" verdict (internal/patternstore/store.go:18-24) not shown in docs
  (reasonable — it routes to the LLM).
  PROOF: internal/store/types.go:38, 79; main.go:1444-1481.
  RECOMMENDED FIX: Footnote in the verdict table: "evidence_unavailable is a
  resolution state applied on top of a finding's verdict, not a verdict
  itself."

[3.4] "No pattern was learned" in the Netgear walkthrough — nuance
  CLAIM (README:53): "No pattern was learned (malicious verdicts deliberately
  do not auto-learn broad patterns)."
  ACTUAL: For malicious verdicts the exact normalized HASH is learned; only
  broad patterns (prefix/regex/contains) are withheld — "learn the hash but
  NOT patterns (conservative trust model)".
  PROOF: internal/analyzer/analyzer.go:611.
  RECOMMENDED FIX: "Only the exact hash was cached; no broad pattern was
  learned."
